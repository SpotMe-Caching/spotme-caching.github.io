SpotMe
Caching

Geocaching, aber ohne Tupperdose im Gebüsch. Spots setzen, teilen, finden – und dann auch noch jemanden treffen, der ebenfalls hingeht.

PWA mobile-first Vanilla JS keine Frameworks Node + Express Backend PostgreSQL via Neon MIT Open Source

Was ist das?

Eine Progressive Web App, die direkt im Browser läuft. Kein App-Store, kein Installationsmarathon.

Klassisches Geocaching heißt: Dose suchen, Zettel unterschreiben, heimgehen. SpotMe packt eine soziale Ebene drauf: Du setzt einen Spot mit Foto und Beschreibung, andere entdecken ihn, schicken dir eine Einladung, und wenn ihr beide wirklich vor Ort seid, wird eingecheckt – inklusive Match-Screen. Dazu gibt’s Profile, Chat, Wetter, Navigation und ein paar Datenschutz-Regeln, die ernster gemeint sind, als man es bei einem Hobbyprojekt erwarten würde.

Motto: „Nicht jeder Spot ist auf der Karte. Manche muss man sich verdienen.“

Features

Alles, was die App heute kann. Ohne Marketing-Nebel.

🗺️ Karte

  • MapLibre GL mit OpenFreeMap-Tiles – kein API-Key, kein Ärger
  • Eigene Marker in Amber, fremde mit Online-Status
  • Kategorie-Filter als Pills über der Karte
  • Radius-Suche (2 / 5 / 10 km), sortiert nach Entfernung, mit Wetter-Badge
  • „Neue Spots“: letzte 24 h im 2-km-Umkreis

🧭 In-App-Navigation

  • Vollbild-Overlay mit Live-GPS (watchPosition)
  • Fußweg über OpenRouteService foot-hiking, Auto über OSRM
  • Neuberechnung erst nach 25 m – kein API-Spam
  • Distanz, Fuß- und Fahrzeit immer sichtbar

📍 Spots

  • Eigene Erstellungsseite mit Kategorie, Tageszeit, Andrang, Intimität
  • Foto-Upload mit Canvas-Komprimierung (JPEG 72 %)
  • Bearbeiten, löschen oder per Soft Delete deaktivieren
  • Wetter für die nächsten 8 Stunden (Open-Meteo)
  • Neue Fotos brauchen die Freigabe vom Admin

🗓️ Wochen-Spots

  • Privater Spot, der nach 7 Tagen von selbst verschwindet
  • Link teilen, fertig – Besucher brauchen keinen Login
  • Anonyme Check-ins („Anonym #1, #2 …“)
  • Live-Countdown auf spot-woche.html

📡 Live Spots

Standort live für Freunde freigeben. Gedacht für spontane Treffen. Freiwillig, ein Spot zum Einschalten.

📨 Einladungen

  • Einladung mit Zeitfenster, annehmen oder ablehnen
  • GPS-Check-in im 50-m-Radius
  • Match-Screen und gegenseitige Verifikation
  • Abgelaufene Einladungen: erst archiviert, nach 30 Tagen gelöscht

💬 Chat

  • Direktnachrichten an Spot-Inhaber, auch ohne Einladung
  • WhatsApp-artige Chatliste mit Ungelesen-Zähler
  • Offline-Nachrichten kommen an, sobald der andere wieder da ist
  • Echtzeit-Teil läuft über PeerJS (WebRTC) im Ordner chat/

👤 Profile

  • Anzeigename, Geburtsjahr (einmalig), Region, Bio, Wünsche und Angebote als Chips
  • Avatar mit Admin-Moderation
  • Backup und Restore als JSON-Datei

🔐 Datenschutz

  • Dein Standort ist auf der Karte für andere unsichtbar
  • Andere sehen nur ● online / ○ offline
  • Profildaten liegen serverseitig AES-256-CBC-verschlüsselt
  • Fotos erscheinen erst nach Freigabe

📱 PWA & Extras

  • Installierbar auf iOS und Android, offlinefähig per Service Worker
  • Wegpunkte, Routen-Erstellung, Bluesky-Anbindung, Wetter-Modul
  • Mehrsprachig: de / en / es (Ordner locales/)
  • Hilfe-Bereich (help/), Android-Wrapper (android-app/)

Architektur

Frontend liegt auf GitHub Pages, das Backend auf Render, die Daten bei Neon. Drei Hosts, null Serverwartung im Wohnzimmer.

Browser / PWAVanilla JS + Service Worker
⇄
GitHub PagesHTML, CSS, JS
→
RenderNode + Express + PeerJS
→
NeonPostgreSQL

Der Browser holt sich die Seiten von GitHub Pages und redet für alles Dynamische mit dem Express-Server. Der Server verschlüsselt Profildaten, hält die Moderationsqueue und erledigt Push-Nachrichten (web-push) und Bluesky-Posts (@atproto/api). Externe Dienste für Tiles, Routing und Wetter spricht der Client direkt an.

Setup

In zehn Minuten läuft das Ding. Versprochen, wenn Neon nicht gerade Kaffeepause hat.

Voraussetzungen

Node.js ≥ 18 und eine PostgreSQL-Datenbank (Neon reicht völlig).

Backend starten

npm install
DATABASE_URL=postgres://... \
ADMIN_KEY=dein-geheimer-key \
CRYPTO_KEY=$(openssl rand -hex 32) \
node server.js

Die Tabellen legt initDB() beim ersten Start selbst an, inklusive weekly_spots. Migrationen von Hand gibt’s nicht.

Environment-Variablen

VariableWofür
DATABASE_URLPostgreSQL-Connection-String (Neon oder Render)
ADMIN_KEYPasswort fürs Admin-Panel
CRYPTO_KEY64 Hex-Zeichen für die AES-Verschlüsselung (openssl rand -hex 32)
PORTStandard 3000, Render setzt es selbst
CRYPTO_KEY gut aufheben. Ohne ihn sind alle verschlüsselten Profile Datenmüll. Neu erzeugen heißt: alle Profile weg.

Fußweg-Routing aktivieren

Kostenlosen Key bei openrouteservice.org holen und in index.html eintragen (Zeile ca. 902):

const ORS_KEY = 'dein-ors-key-hier';

Ohne Key fällt die App auf OSRM foot zurück, das kennt aber nur befestigte Wege.

Frontend deployen

  1. Alles auf GitHub Pages pushen.
  2. CACHE_VERSION in sw.js um 1 erhöhen.
  3. Fertig. Der Service Worker registriert sich von selbst.
const CACHE_VERSION = 'v9'; // bei jedem Deploy hochzählen
Warum das so wichtig ist: Statische Dateien laufen per Stale-While-Revalidate. Ohne neue Version sehen Nutzer munter weiter den alten Stand, und du suchst Bugs, die längst gefixt sind.

Stolperfallen & Befunde

Die ehrliche Ecke. Hier steht, was beim Durchlesen aufgefallen ist.

Das README hinkt hinterher. Die Dateistruktur dort nennt 9 Dateien, im Repo liegen deutlich mehr (Live Spots, Wegpunkte, Routen, Messenger, Leaderboard, chat/, locales/ …). Auch Push, Bluesky und PeerJS fehlen im Text, obwohl sie in package.json stehen. Wer neu einsteigt, kriegt ein zu kleines Bild.
Datenschutz-Versprechen und Live Spots. Das README sagt, der eigene Standort sei für andere nie sichtbar. Live Spots teilen ihn aber live mit Freunden. Das ist okay, weil freiwillig – aber der Satz sollte das sagen: „…außer du aktivierst einen Live Spot.“
Das Backup ist ein Schlüsselbund. Die JSON-Datei enthält Code und Token. Wer sie in die Finger kriegt, ist du. Nutzer sollten das vor dem Download lesen, nicht danach.
AES-256-CBC hat keine Manipulationserkennung. Für Profildaten geht das. Wer später nachrüsten will: AES-256-GCM prüft die Integrität gleich mit. Alte Daten müssten einmal umgezogen werden.
Der ORS-Key steckt im Frontend. Das ist bei reinen GitHub-Pages-Apps nicht vermeidbar. Im ORS-Dashboard das Kontingent im Blick behalten, und der Key sollte nur dafür taugen, wofür er gedacht ist.
CACHE_VERSION vergessen ist der Klassiker Nummer eins. Siehe Setup.
PeerJS: „ID is taken“. Wird initWebRTC doppelt aufgerufen, versucht die Seite zweimal dieselbe Peer-ID zu belegen. Einmalig initialisieren und die Instanz wiederverwenden.
Eine Quelle der Wahrheit. Zwei Versionen derselben Datei parallel zu bearbeiten hat schon Regressionen gebracht. Eine Datei, ein Stand.
Stand dieser Analyse: Gelesen wurden README, package.json, news.md und die Dateiliste. Die Quelltexte (server.js, index.html, sw.js, Unterordner) waren nicht abrufbar. Details zu Live Spots, Push und Bluesky bitte gegen den Code prüfen.

Roadmap

Was schon steht und was noch kommt.

✅ Läuft

  • Spots setzen, bearbeiten, deaktivieren
  • Kategorien, Filter, Radius-Suche
  • Einladungen, Check-in, Verifikation
  • Chat mit Offline-Zustellung
  • Wochen-Spots, Live Spots
  • In-App-Navigation (Fuß + Auto)
  • Backup/Restore, Moderation, AES-Verschlüsselung
  • Service Worker, Wetter

🔜 Kommt

  • Ankunftserkennung: „Du bist da“ bei unter 20 m
  • SSE statt Polling: Express-SSE plus LISTEN/NOTIFY, sinnvoll ab ca. 500 gleichzeitigen Nutzern
  • Besuchshistorie im Profil
  • Marker-Clustering
  • Haptik bei Check-in und neuer Nachricht
  • Spot-Ablaufdatum durch den Eigentümer
